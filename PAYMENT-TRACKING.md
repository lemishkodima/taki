# Відстеження продажу квитків ТАКІ

Код підготовлено локально. Події ще потрібно підключити до акаунтів і перевірити після деплою. Локальні тести використовують заглушки: вони не проводять оплат і не відправляють подій у Meta.

## Що реалізовано

- Pixel ID: `1415065917256078`.
- `InitiateCheckout` — браузерна подія після валідного надсилання форми купівлі, перед переходом на WayForPay. Переходи до секції «Квитки» не рахуються. Невідома остаточна сума не передається. Блокування Pixel не заважає оплаті.
- `Purchase` — серверна подія Conversions API після підписаного повідомлення WayForPay зі статусом `Approved` та кодом `1100`. Сума — `amount` з транзакції; валюта має бути `UAH`. Вона не залежить від ціни в HTML і включає весь оплачений обсяг замовлення.
- На сторінці `/thank-you` немає події Purchase. Повторне відкриття цієї сторінки не впливає на продажі.
- Окреме сховище не використовується. Кожне підтверджене повідомлення надсилається в Meta зі стабільним `event_id`, утвореним із мерчанта й номера замовлення, та часом транзакції `processingDate`. Усунення дублів покладається на Meta; локального журналу вже переданих покупок немає.
- Для зіставлення покупця Meta отримує SHA-256 хеші email/телефону. У платіжній формі потрібно збирати хоча б один із цих контактів. Номер картки та токен картки до Meta не передаються й не зберігаються.
- За поточного зовнішнього платіжного посилання немає надійного зв’язку замовлення з браузерними `fbp/fbc`: зіставлення Purchase працює за контактами покупця. Для точнішої рекламної атрибуції потрібне окреме створення замовлень із передаванням ідентифікаторів браузера.

## Підключення на Vercel

У Settings → Environment Variables додайте серверні змінні. Не вставляйте секрети в HTML, JavaScript браузера, Git або чат.

| Змінна | Значення |
| --- | --- |
| `WAYFORPAY_MERCHANT_ACCOUNT` | Merchant Login саме магазину, що приймає оплату квитків |
| `WAYFORPAY_SECRET_KEY` | Secret Key цього магазину |
| `META_CAPI_ACCESS_TOKEN` | Токен Conversions API для пікселя 1415065917256078 |
| `META_GRAPH_API_VERSION` | `v25.0` |
| `TRACKING_MODE` | `live` для Production |

Обов’язкові лише три секретні/облікові змінні: логін WayForPay, ключ WayForPay та токен Meta. Окрему базу створювати не потрібно. `META_GRAPH_API_VERSION` і `TRACKING_MODE` мають указані вище значення за замовчуванням. Для production залиште `META_TEST_EVENT_CODE` порожнім/відсутнім.

Зробіть деплой. Це статичний сайт із Node.js Vercel Function у `api/wayforpay-webhook.js`; не публікуйте лише HTML та картинки без папок `api` і `lib`. Обробник не працює на простому Python static server.

## Налаштування WayForPay

У налаштуваннях саме платіжної сторінки/кнопки конференції встановіть Service URL:

`https://www.taki.org.ua/api/wayforpay-webhook`

Не використовуйте webhook для інших товарів того ж мерчанта. Якщо вже є інший Service URL, збережіть його та узгодьте пересилання: цей обробник не виконує чужі інтеграції автоматично.

Approve URL після успіху можна залишити `https://www.taki.org.ua/thank-you`. Service URL і Approve URL виконують різні функції. Потрібен фінальний статус списання `Approved`, а не холдування `WaitingAuthComplete`.

Перевірте фактичну суму й можливість кількох квитків у WayForPay. Зміна виділення ціни на лендінгу 1 жовтня сама по собі не змінює вартість у платіжному кабінеті.

## Test Events і тестова транзакція

1. InitiateCheckout: після деплою відкрийте сайт через Test Events у Meta Events Manager, натисніть «Купити квиток» із погодженням. Має бути одна браузерна InitiateCheckout; Purchase на цьому кроці бути не повинно.
2. Purchase без реального списання: використайте окремий Preview deployment та тестовий мерчант WayForPay з офіційних тестових реквізитів. Не перемикайте бойову кнопку на публічного тестового мерчанта.
3. Для Preview задайте тестові `WAYFORPAY_MERCHANT_ACCOUNT` / `WAYFORPAY_SECRET_KEY`, `TRACKING_MODE=test` і `META_TEST_EVENT_CODE` із вкладки Test Events. Додайте токен Meta. Зробіть новий Preview deploy. Код блокує тестовий режим на Vercel Production.
4. У тестовій платіжній формі задайте Service URL цього Preview deployment, доступний для WayForPay без сторінки входу. Тестова платіжна форма не створена цим оновленням; використайте тестовий магазин/інтеграцію WayForPay. Наявна бойова кнопка залишається бойовою.
5. Проведіть транзакцію тестовими реквізитами WayForPay. У Test Events шукайте серверний Purchase з фактичними `value` і `currency: UAH`. Код Test Events сам по собі не робить реальну оплату тестовою.
6. Перевірте одну оплату, кілька квитків, відмову, незавершену оплату та повторну доставку callback. Після відмови/холду Purchase не має бути. Для повторних повідомлень перевірте незмінність `event_id` і фактичну дедуплікацію в Meta; локальні тести не підтверджують поведінку Meta.
7. Перевірте пряме відкриття `/thank-you`: тільки PageView, без Purchase.

Серверна Purchase відображається в Events Manager як Server, а не Browser. Не додавайте паралельне правило Purchase за URL сторінки «Дякуємо» в Event Setup Tool: воно створить хибні/дубльовані продажі.

## Доставка й діагностика

Успішний webhook повертає підписану відповідь `accept` лише після прийняття події Meta. Відмови/проміжні статуси підтверджуються без подій. Некоректний підпис повертає 401, недоступність налаштувань/Meta — 503, щоб WayForPay повторив запит.

WayForPay повторює повідомлення до 4 діб. Повторні й паралельні callback можуть спричиняти повторні HTTP-запити в Meta, завжди з тим самим `event_id` для замовлення. Це очікувана поведінка версії без сховища. Вона не гарантує одноразового зарахування поза вікном дедуплікації Meta, зокрема при пізніх повторах. Не генеруйте новий ID чи поточний час для повтору. Автоматичного відсікання через 47 годин більше немає: сервер не пам’ятає час першої спроби. Після тривалих збоїв звіряйте статистику Meta з транзакціями WayForPay. Налаштуйте моніторинг помилок webhook.

Токени, payload callback і відповіді Meta з персональними даними не логуються. Відсутність контактів позначається `missing_payer_contact`: перевірте платіжну форму.

## Локальні перевірки

`node --test tests/*.test.cjs`

Перевірено: валідне оформлення, повернення назад, недоступний Pixel, підпис, фактичні суми/кількість квитків, інші статуси, стабільні ID для повторних/паралельних callback та після перезапуску сервера, збої Meta і відокремлення тестових подій.
